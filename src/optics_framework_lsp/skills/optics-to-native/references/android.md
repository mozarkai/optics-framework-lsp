# Android script (uiautomator2)

One Python file. `assets/uiautomator2_example.py` is the core to copy; step 7 of `SKILL.md`
then adds `assets/uiautomator2_run_output.py` to it. Top to bottom:

| Part | What goes there |
| --- | --- |
| Header comment | Replace the example's first line. Say the script was written from an optics suite by the optics-to-native skill (not generated by `optics-lsp generate`), name the suite, and keep the note that an element's locators are tried in order but optics' OCR, image and self-heal fallbacks are not carried - the step fails |
| Imports | The example's, plus `json`, `os`, `xml.etree.ElementTree as ET` and `datetime` (Part 1 of the run-output asset), plus `ast`, `csv`, `io` and `re` when the flow-control or data patterns use them |
| `SERIAL`, `PACKAGE`, `ACTIVITY` | From `config.yaml`: `udid` (else `deviceName`), `appPackage`, `appActivity`, as string literals, or `os.environ['NAME']` for an `ENV:NAME` value. `deviceName` is only a label for an emulator ("Android Emulator"); `u2.connect` needs the serial |
| `WAIT_TIMEOUT`, `POLL_INTERVAL`, `STEP_DELAY`, `OUT` | Part 1 of the run-output asset. `OUT` replaces the example's `OUT = Path(__file__)…` with `EXEC_OUTPUT` |
| `VARS`, `SOFT` | Unchanged |
| Helpers `_selector` … `_write_pagesource` | The runtime. Unchanged, except `time.sleep(0.2)` becomes `time.sleep(POLL_INTERVAL)` and the corrections below |
| Variable store, flow control, data | Only what the suite uses, from `references/code-patterns.md` |
| Error detection, reports, source map | Part 2 of the run-output asset, with `ERRORS` filled from the suite's error definitions |
| `ELEMENTS` | Every element that has a usable locator, whether or not a step uses it as a locator - value-only ones (`4`, `com.teststudio`) and ones a run-time expression reads, such as `Evaluate`'s operands, stay in: `'name': ['locator', 'fallback', ...]` in suite order, with refused locators left out |
| `# Modules` | One `def <name>(d):` per module, its docstring the original name, one line per step |
| `# Test cases` | One `def test_<name>(d):` per test case, its docstring the original name, then the `TESTS` list in suite order |
| `main()` and the `__main__` guard | Part 3 of the run-output asset |

## Steps in a module

One line per step, ending with the source comment; the origin call goes on the line before.
A step that takes several lines (a `Run Loop`'s `for`, a `_condition([...])`) carries the
comment on its first line. The post-step screenshot is the line after the step, for a step
whose keyword's owner is `ActionKeywords` or `AppManagement` (not `Sleep`). Typing steps
dismiss the keyboard on the step's own line, before the screenshot:

```python
    _origin('modules.csv:7 Press Element')
    _find(d, ELEMENTS['login_button']).click()  # modules.csv:7 Press Element
    _post(d, 'Press Element')
    _origin('modules.csv:8 Enter Text')
    _find(d, ELEMENTS['user']).set_text('demo'); _hide_keyboard(d)  # modules.csv:8 Enter Text
    _post(d, 'Enter Text')
```

An `assert` always carries a message that names the keyword, the element and the wait, so
the report's `reason` says what failed - `assert _wait(d, ELEMENTS['home_title'], 20,
'any'), "Validate Element: home_title not found within 20s"` - not just the origin.

## Test functions

A test function never calls a module directly. It goes through `_step`, which records the
module as one step of the test case in the report, runs it, and marks every later module
`NOT RUN` once one has failed:

```python
def test_login(d):
    'Login'
    _step(d, 'Launch Optics App', launch_optics_app, 'AppManagement')  # test_cases.csv:2
    _step(d, 'Verify Home Screen', verify_home_screen, 'Verifier')  # test_cases.csv:3
```

`owner` is the optics class that defines the keyword of the module's first step - see
`references/run-output.md`.

## Corrections to the example runtime

The example's runtime was checked on an emulator and two helpers are wrong for optics. Apply
both; they are the only changes allowed to the helpers besides `POLL_INTERVAL`.

- **`Scroll` and `Scroll Until Element Appears` go the other way.** optics `scroll("down")`
  drags the finger from 80% to 20% of the screen height - the content moves down - and
  uiautomator2's `swipe_ext("down")` does the opposite. Emit `d.swipe_ext('up')` for
  `Scroll, down` and `d.swipe_ext('down')` for `Scroll, up`; in `_swipe_until`, call
  `d.swipe_ext` with the flipped direction when the keyword is `Scroll Until Element
  Appears` (`Swipe Until Element Appears` swipes with the finger and stays as it is). The
  helper does not know the keyword, so give it a `flip` parameter and pass `flip=True` at the
  call site of `Scroll Until Element Appears`:

  ```python
  def _swipe_until(d, value, direction, timeout, flip=False):
      direction = {"up": "down", "down": "up"}.get(direction.lower(), direction.lower()) if flip else direction.lower()
      ...  # the rest unchanged, ending in d.swipe_ext(direction)
  ```
  optics supports only `up` and `down` for `Scroll`; for anything else it logs and does
  nothing, so emit nothing.
- **`_wait_visible` never passes for an xpath locator.** It reads `visibleBounds`, which only
  `d(...)` selectors have; an `d.xpath(...)` element has `bounds` and `visibleToUser`.
  Replace the two lines that compute `box` with:

  ```python
  info = element.info if element is not None else {}
  box = info.get("visibleBounds") or (info.get("bounds") if info.get("visibleToUser") else None)
  ```
- **Typing leaves the keyboard open.** optics types with Appium's `send_keys`, which never
  raises the soft keyboard; uiautomator2's `set_text` taps the field first, so the keyboard
  comes up and the suite's next Back key only dismisses it. Add this helper and call
  `_hide_keyboard(d)` right after every `.set_text(...)` (Enter Text, Enter Number, Clear
  Element Text):

  ```python
  def _hide_keyboard(d):
      if "mInputShown=true" in d.shell("dumpsys input_method").output:
          d.press("back")
  ```

  Do not use `d.hide_keyboard()`: it installs a keyboard app and changes the device's input
  method.
## Names

- A function name is the block name lowercased, with every run of other characters
  replaced by `_` (`Sign In` → `sign_in`, test cases get `test_`). A name starting with a
  digit gets `m_` in front.
- Two blocks that land on the same name, or a name the script already uses (`main`, `sys`,
  `time`, `u2`, `d`, a Python keyword), get `_2`, `_3` … in suite order. Calls use the
  assigned name.

## Values

- A literal param is a Python string: `'demo_user'`.
- A locator param holding an element is `ELEMENTS['name']`.
- A value param holding an element is that element's first value, inlined as a literal -
  unless the suite also writes that name at run time (`Read Data`, `Evaluate`, `Run Loop`,
  `Get Text`), in which case it is `_var('name')`, because the value changes.
- `ELEMENTS` keeps an element that is also written at run time (`profile_name`): `_var` falls
  back to its listed value until the suite writes one.
- A run-time variable is `_var('name')` (from `references/code-patterns.md`) - `VARS` holds
  lists, so never pass `VARS['name']` itself.

## Running it

`pip install uiautomator2` (and `requests` when it calls an API), a booted device or emulator, then `python <file>`. It prints `PASS`/`FAIL` per test
case, writes the files in `references/run-output.md` to `EXEC_OUTPUT`, and exits non-zero if
any test case failed.
