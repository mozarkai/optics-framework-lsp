# iOS script (XCUITest)

One Swift file holding one `XCTestCase`. `assets/xcuitest_example.swift` is the core to copy;
step 7 of `SKILL.md` then adds `assets/xcuitest_run_output.swift` to it. Top to bottom:

| Part | What goes there |
| --- | --- |
| Header comment | Replace the example's first line. Say the script was written from an optics suite by the optics-to-native skill (not generated by `optics-lsp generate`), name the suite, and keep the note that an element's locators are tried in order but optics' OCR, image and self-heal fallbacks are not carried - the step fails |
| `import XCTest`, the class line | Unchanged (the class name is only a name) |
| `app`, `soft` | Unchanged. The example's `vars` is not used: the static `store` of `references/code-patterns.md` replaces it, because XCTest makes a new instance for every test method |
| Members after `soft` | Part 1 of the run-output asset, with `BUNDLE_ID` from the config's `bundleId` and `errors` filled from the suite's error definitions |
| `setUpWithError`, `tearDownWithError` | Replaced by Part 2 of the run-output asset, which also adds the class `setUp`/`tearDown` and the run-output helpers |
| `// MARK: elements` → `ELEMENTS` | Every element that has a usable locator, whether or not a step uses it as a locator: `"name": ["locator", "fallback", ...]` in suite order, with refused locators left out |
| `IMPLICIT_WAIT`, `ATTRIBUTES`, `TYPE_IDS` | Unchanged, except `IMPLICIT_WAIT` and the sleep in `waitUntil` read their settings as Part 1 of the asset says |
| `// MARK: locators`, `waiting`, `acting` | Unchanged - the runtime, including the on-device xpath resolver - apart from the corrections below |
| `// MARK: modules` | One `func <name>()` per module, one line per step, each step preceded by `origin("file:line Keyword")` |
| `// MARK: test cases` | One `func test<NN><Name>()` per test case: `begin(...)` listing its modules, then one `step(...)` per module |

## Test functions

XCTest runs the test methods of a class in alphabetical order, so each test case's name starts
with its two-digit position in the suite (`test01Login`, `test02Transfer`, ...); with more than
99 test cases use three digits. A test function lists its modules once in `begin`, then calls
each through `step`:

```swift
/// Login
func test01Login() {
    begin("Login", [("Open App", "AppManagement"), ("Sign In", "ActionKeywords")])
    step("Open App", "AppManagement") { openApp() }  // test_cases.csv:2
    step("Sign In", "ActionKeywords") { signIn() }  // test_cases.csv:3
}
```

A failing step ends the test case, as it does in optics; the modules after it are reported
`NOT RUN` from the list in `begin`, so list every module, in order. `owner` is the optics class
that defines the keyword of the module's first step - see `references/run-output.md`.

## Steps in a module

One line per step; the origin call goes on the line before it (that line is the source map: a
module's steps need no trailing comment, a test function's `step(...)` lines carry one), and a post-step screenshot
(`post("Keyword")`) after it for a step whose keyword's owner is `ActionKeywords` or
`AppManagement` (not `Sleep`). An assertion always carries a message naming the keyword, the
element and the wait, so the report says what failed:

```swift
origin("modules.csv:7 Press Element")
el("login_button").tap()
post("Press Element")
origin("modules.csv:8 Validate Element")
XCTAssertTrue(waitForAll("home_title", Double("20") ?? 30, "any"), "Validate Element: home_title not found within 20s")
```

## Corrections to the example runtime

- **`typeInto` and `clearText` hold a stale handle.** `el(name)` is a chain of child indexes,
  and tapping a field (a search field, say) changes the hierarchy, so the same handle can no
  longer be resolved for the `typeText` that follows and the step fails with "Failed to get
  matching snapshot". Resolve again after the tap:

  ```swift
  func typeInto(_ name: String, _ text: String) {
      el(name).tap()
      el(name).typeText(text)
  }
  ```

  and in `clearText` call `el(name)` for each of `.value`, `.tap()` and `.typeText(...)`
  instead of keeping it in a `let`.

- **`Scroll` and `Scroll Until Element Appears` go the other way.** optics `scroll("down")`
  moves the finger up (the content moves down), and `swipeScreen("down")` does `swipeDown()`,
  the opposite. For `Scroll`, emit `swipeScreen("up")` for `down` and `swipeScreen("down")` for
  `up`; for `Scroll Until Element Appears`, give `swipeUntil` a flip parameter and pass it at
  the call site (`Swipe Until Element Appears` swipes with the finger and stays as it is).
  optics supports only `up` and `down` for `Scroll`; for anything else it does nothing.

## Names

- A function name is the block name in lowerCamelCase (`Sign In` → `signIn`), with `m` in
  front if it starts with a digit. A test case is `test` + UpperCamelCase (`Login` → `testLogin`).
- Clashes with each other, with a Swift keyword, or with a name the runtime declares get
  `_2`, `_3` … in suite order. Calls use the assigned name.

## Values

- A literal param is a Swift string: `"demo_user"`.
- A locator param holding an element is passed by **name**, as a string: `el("login_button")`.
  The runtime looks the name up in `ELEMENTS` at run time, so a wait re-resolves instead of
  holding a stale handle.
- A value param holding an element is its first value, inlined as a literal.
- A run-time variable is `v("name")` (from `references/code-patterns.md`).

## How an xpath runs

XCTest has no xpath, and a query is not a translation of one: an xpath index counts within
each parent while a query flattens every match into one list, and the tree a query walks is
not the tree a page source shows. So **an xpath is never rewritten into a query.** Put it in
`ELEMENTS` exactly as the suite wrote it; the runtime evaluates it on the device each time a
step needs it:

1. `snapshotTree()` captures the live hierarchy as `Node`s - type, `name`, `identifier`,
   `label`, `value`, and the node's `path` as a chain of child indexes.
2. `parseXPath(_:)` splits the xpath into steps; `evaluate(_:in:)` runs them against the
   snapshot, `apply(_:to:)` doing one step against one context node.
3. `predicate(_:)` turns each `[...]` test into an `NSPredicate`.
4. `element(at:)` walks a match's `path` back to a live `XCUIElement` through
   `children(matching: .any)`, which enumerates in the same order as the snapshot.
5. `lookup(_:_:_:)` does this for one locator; a plain string is matched on
   `identifier`, `label` or `value` instead. `resolve(_:_:)` tries an element's locators
   in order and returns the first that exists.

Steps call it by element name only: `el("login_button")`, `elAt("row", "2")`,
`waitFor(...)`, `matches(...)`. Never build an `XCUIElementQuery` in a step.

What the evaluator reads - anything else makes it match nothing, so refuse the locator
instead:

| Part | Supported |
| --- | --- |
| Steps | `/child` and `//descendant` |
| Node test | `*`, or a full type name: `XCUIElementTypeButton`, not `Button` |
| Index | `[2]` (1-based, within each parent), `[last()]`, and `(//path)[2]` over the whole result |
| Predicate attributes | `@name`, `@identifier`, `@label`, `@value`, `@type`, `@elementType` |
| Predicate operators | `=`, `!=`, `and`, `or`, `contains(@a,'x')`, `starts-with(@a,'x')`, `ends-with(@a,'x')`, with single or double quotes |


## Configuration

From `config.yaml`'s `appium` capabilities (also accepted with an `appium:` prefix):

- `bundleId` → `BUNDLE_ID`. `setUpWithError` (Part 2 of the run-output asset) creates the app
  with `XCUIApplication(bundleIdentifier: BUNDLE_ID)`, so every step drives that app; with no
  `bundleId`, change that line to `XCUIApplication()` (the UI-test target's own app). A
  `Launch App` step naming a bundle id still overrides it.
- `ENV:NAME` values are read with `ProcessInfo.processInfo.environment["NAME"]` and fail the
  test when unset - pass them through the test plan's environment variables.
- `udid` is not set in code: it picks the device, so put it in the run command,
  `xcodebuild test -destination 'id=<udid>'`, and say so in the report.

## Running it

Add the file to an existing Xcode UI-test target, then run the tests on a simulator or
device:

```
TEST_RUNNER_EXEC_OUTPUT=/some/folder xcodebuild test -project <proj> -scheme <scheme> \
  -destination 'id=<udid>' -only-testing:<UITestTarget>/<ClassName>
```

The report files go to `EXEC_OUTPUT` (any `TEST_RUNNER_` variable reaches the tests without the
prefix); with none set, to `NSTemporaryDirectory()/output` inside the test runner's container.
A simulator shares the host's file system, so a host folder works there; on a device, read the
attachments from the result bundle instead.
